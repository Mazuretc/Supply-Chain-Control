## 1. Что это за система

**Lovarus (Supply Chain Control)** — внутренняя система контроля заказов поставщикам. Она нужна, чтобы сотрудники компании видели единую картину по срокам: согласование, производство, отгрузка и доставка.

Система связывает:

- заказы поставщику (supplier orders);
- ERP-позиции внутри этих заказов;
- источники сроков (ERP, письма, Excel, расчёты);
- отклонения от плана и позиции, которые требуют внимания.

Развёртывание: **локальный сервер компании в LAN**. Доступ только у сотрудников и системных администраторов внутренней сети. Публичный интернет-сервис не предполагается.

---

## 2. Для кого и как используется

| Роль | Что видит и делает |
|---|---|
| Обычный сотрудник | Только просмотр: список заказов, фильтры, детали, источники, «требует внимания». Редактировать сроки и связывать ERP нельзя. |
| Системный администратор | Отдельная серверная панель: почтовые ящики, из которых система читает письма и Excel; журнал изменений; ошибки обработки и повторный запуск. Сроки вручную не правит. |

Обычный вход в интерфейс остаётся клиентским (логин/пароль в браузере). Это принято сознательно: доступ к приложению и так ограничен локальной сетью и системными администраторами.

Админ-панель так оставлять нельзя: почтовые пароли и управление ящиками должны проверяться **на сервере**.

## 3. Что уже есть в интерфейсе (MVP)

Текущий frontend — рабочий прототип на Vite + React + TypeScript + Tailwind + Zustand.

Экраны:

1. **Вход / регистрация** — логин и пароль, регистрация новых пользователей в браузере.
2. **Контроль заказов** — группировка по заказу поставщику, KPI, поиск, фильтры, таблица ERP-позиций.
3. **Карточка ERP-позиции** — сроки, источники, конфликты данных, timeline этапов.
4. **Карточка заказа поставщику** — сводка и связанные ERP-позиции.
5. **Требует внимания** — просрочки, предупреждения, отсутствие данных.
6. **Несвязанные данные** — ERP-позиции без заказа поставщику.
7. **Источники** — счётчики ERP / email / расчёт / вручную и статус интеграций.

Также сделано:

- адаптивная вёрстка (выезжающее меню на узком окне, горизонтальный скролл таблиц);
- сессия пользователя сохраняется между перезапусками браузера.

Ограничение текущей версии: данные берутся из `src/lib/mockData.ts` и живут в памяти вкладки. Кнопка «Обновить данные» и статусы интеграций пока фиктивные.

## 4. Согласованные решения

Эти пункты уже обсуждены и считаются правилами проекта. Их нельзя менять «по ходу», только отдельным решением.

### 4.1. Что оставляем как есть

- Обычная авторизация остаётся в браузере.
- Пароли обычных пользователей можно хранить на клиенте: доступ к системе только у сотрудников LAN и сисадминов.
- Обычный пользователь **только смотрит**. Редактирования, подтверждения конфликтов и связывания ERP у него не будет.
- Защита от одновременного редактирования не нужна: править некому.

### 4.2. Что обязательно делаем на сервере

- Общая база данных PostgreSQL.
- Внутренний API: все сроки и изменения проходят через сервер.
- Отдельный профиль администратора с серверной сессией.
- Админ управляет почтовыми ящиками (адрес, пароль, IMAP-сервер), из которых система читает письма и Excel.
- Журнал изменений виден только в админ-панели.
- Администратор **не редактирует и не подтверждает сроки**. Система выбирает значение сама по правилам ниже.

### 4.3. Технологии

| Вопрос | Решение |
|---|---|
| База данных | PostgreSQL |
| Backend | Node.js + TypeScript + NestJS |
| Frontend | текущий React в корне репозитория |
| Почта | IMAP: адрес, пароль приложения, сервер, порт |
| Анализ писем | текст письма + вложения `.xlsx` / `.xls` |
| Извлечение сроков из текста | корпоративный GPT, OpenAI-compatible API (`baseUrl`, `apiKey`, `model` только на сервере) |
| Сервер компании | Windows Server / IIS |
| Архитектура | модульный монолит: один backend-проект, API и IMAP-worker как два процесса, общая PostgreSQL |
| Администратор | одна серверная учётная запись; пароль задаётся при развёртывании |

### 4.4. Правило выбора срока

Если по одному полю пришло несколько значений:

1. Значение из **текста письма всегда выше Excel**, даже если Excel новее.
2. Среди нескольких текстовых значений берётся **самое новое письмо**.
3. Если текста нет — берётся **самый новый Excel**.
4. Невалидная дата, неизвестный заказ или низкая уверенность GPT **не обновляют срок**. Создаётся ошибка в админ-панели.

### 4.5. Хранение почты

Через **90 дней** удаляются тексты писем и бинарные вложения.  
Актуальные сроки заказа, ссылки на источник, технические метаданные и журнал изменений **сохраняются**.

### 4.6. Безопасность админ-части

- Пароль администратора хранится только как Argon2-хеш.
- IMAP-пароли шифруются AES-256-GCM ключом из защищённой переменной Windows.
- Показать исходный пароль ящика можно только после повторного ввода пароля администратора; каждое раскрытие пишется в журнал.
- Админ-сессия: HTTP-only cookie, таймаут, CSRF, ограничение попыток входа.
- IIS завершает HTTPS и проксирует `/api`.
- API и worker запускаются отдельными Windows-службами.
- Ежедневный backup PostgreSQL и проверяемое восстановление.

## 5. Целевая архитектура

```
Сотрудник (браузер, только просмотр)
        │
        ▼
  React-интерфейс  ──►  IIS  ──►  /api  ──►  NestJS API  ──►  PostgreSQL
                                                      ▲
Администратор (серверная сессия) ──►  /api/admin  ────┘
                                                      ▲
IMAP worker  ──►  почтовые ящики                      │
     │                                                │
     ├── Excel parser                                 │
     ├── корпоративный GPT                            │
     └── resolver сроков  ────────────────────────────┘
```

Обычные GET-запросы к данным заказов не требуют серверной идентификации: это принятый LAN-риск.  
Все `/api/admin/*` защищаются серверной cookie-сессией.

## 7. План работ

Работы идут строго по порядку. Каждый этап даёт проверяемый результат.

### Этап 1. Фундамент backend и база

**Цель:** API и PostgreSQL существуют, схема данных готова, mock-данные можно загрузить в БД.

- [ ] Довести NestJS-проект в `server/` до запускаемого API
- [ ] Подключить PostgreSQL через Prisma (схема уже есть в `server/prisma/schema.prisma`)
- [ ] Прогнать миграцию и seed из `src/lib/mockData.ts`
- [ ] Модули: `auth`, `orders`, `mail-accounts`, `mail-ingestion`, `extraction`, `audit`, `jobs`, `retention`

**Проверка:** `server` стартует, в PostgreSQL есть заказы, ERP-позиции и учётная запись администратора.

### Этап 2. Защищённый администратор

**Цель:** только администратор может управлять почтовыми ящиками; пароли ящиков не утекают в браузер.

- [ ] Одна серверная учётка администратора (Argon2)
- [ ] HTTP-only cookie-сессия, таймаут, CSRF, ограничение попыток входа
- [ ] Шифрование IMAP-паролей AES-256-GCM
- [ ] Показ исходного пароля только после повторного ввода пароля администратора + запись в аудит
- [ ] CRUD почтовых ящиков, включение/выключение, проверка соединения

**Проверка:** без админ-сессии `/api/admin/*` недоступен; раскрытие пароля видно в журнале.

### Этап 3. Письма, Excel и GPT

**Цель:** система сама забирает письма и достаёт из них сроки.

- [ ] IMAP worker опрашивает активные ящики
- [ ] Дедупликация по `Message-ID` и хешу содержимого
- [ ] Сохранение метаданных письма и вложений
- [ ] Разбор `.xlsx` и `.xls`, нормализация номеров заказов и дат
- [ ] Адаптер корпоративного GPT (OpenAI-compatible): номер заказа, поле, дата, фрагмент-основание, уверенность
- [ ] Retry с задержкой, идемпотентность заданий, блокировка параллельной обработки одного письма

**Проверка:** тестовые `.eml` / Excel обрабатываются без реальной почты; дубли не создают вторую запись.

### Этап 4. Выбор актуального срока и хранение 90 дней

**Цель:** по каждому полю в заказе одно актуальное значение и понятная история.

- [ ] Транзакционное обновление срока с записью старого/нового значения, источника и времени
- [ ] Правило: текст письма > Excel; среди текста — самое новое письмо; иначе — самый новый Excel
- [ ] Ошибки (плохая дата, неизвестный заказ, низкая уверенность) не меняют срок и попадают в админ-панель
- [ ] Retention: через 90 дней удалять тела писем и вложения, оставлять сроки и аудит

**Проверка:** unit-тесты приоритета источников и retention; история видна администратору.

### Этап 5. Frontend: просмотр + админ-панель

**Цель:** сотрудники работают с живыми данными сервера, администратор управляет почтой.

- [ ] Заменить Zustand/mockData на API-клиент (загрузка, ошибка, ручное обновление)
- [ ] Убрать у обычного пользователя редактирование комментариев, конфликтов и связывание ERP
- [ ] Отдельный вход администратора и страницы: ящики, аудит, ошибки/повтор
- [ ] Реальные статусы источников и время последней синхронизации вместо заглушек

**Проверка:** обычный пользователь только читает; после перезапуска сервера данные на месте.

### Этап 6. Эксплуатация на сервере компании

**Цель:** система ставится на Windows Server и переживает сбой.

- [ ] `.env.example` без секретов
- [ ] Конфиг IIS: раздача frontend, HTTPS, reverse-proxy `/api`
- [ ] API и worker как Windows-службы
- [ ] Инструкция установки PostgreSQL
- [ ] Ежедневный backup и процедура восстановления
- [ ] Runbook обновления и отката

**Проверка:** установка по инструкции, восстановление из backup, повторный вход в интерфейс.

### Этап 7. Приёмка

**Цель:** можно запускать пилот на LAN с тестовой почтой.

- [ ] Unit: приоритет текста над Excel, newest-within-source, дедупликация, даты, 90 дней
- [ ] Integration: PostgreSQL, админ-сессия/CSRF, шифрование, аудит раскрытия паролей
- [ ] Fixtures: тестовые письма и Excel; контракт ответа GPT
- [ ] E2E: сотрудник только читает; администратор управляет IMAP и видит журнал

- Редактирование данных обычными сотрудниками

- Публичный хостинг и доступ из интернета

Эти темы можно открыть после стабильного пилота.

## 10. Критерий готовности пилота

Пилот можно считать готовым, если одновременно верно всё ниже:

1. Сотрудник в LAN открывает Lovarus и видит заказы из PostgreSQL, а не из памяти вкладки.
2. Обновление страницы не теряет данные.
3. Сотрудник не может изменить срок, связь ERP или почтовый ящик.
4. Администратор добавляет IMAP-ящик, система читает письма и Excel, сроки обновляются по согласованным правилам.
5. Журнал изменений и ошибки обработки видны только администратору.
6. Через 90 дней старые письма и вложения удаляются, актуальные сроки остаются.
7. Есть backup PostgreSQL и инструкция восстановления на Windows Server / IIS.
